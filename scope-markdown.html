3.01 Mirror IA & Content Schema

MD-1: ~1.25 Days (OSP)

OSP defines the information architecture and schemas for the machine-readable site mirror — the blueprint everything else builds on.

  • Audit the existing site IA — page types, URL structure, content model in the CMS (Symfony/Contao)
  • Define the .md file tree — which pages get mirrored, routing conventions, naming (/llms/hotel.md, /llms/rooms/deluxe-suite.md, etc.)
  • Front matter schema per page type — metadata fields, language tags, entity references, last-updated timestamps
  • Body template per page type — heading hierarchy, which CMS fields map to which sections, what gets synthesized into prose vs. passed as structured data
  • Cross-entity linking rules — how a room page references the hotel entity, how spa references room packages
  • Multilingual strategy — separate /de/ and /en/ trees vs. single file with language-tagged sections
  • Exclusion rules — nav chrome, booking widgets, legal boilerplate, seasonal/ephemeral content
Deliverable: Mirror IA specification document — the blueprint for the render pipeline. Leverages Jam's schema type map from Phase 1A.
3.02 Render Pipeline

MD-2: ~10.5 Days

Part A — OSP Spec Work (~1.5 days)

OSP writes the requirements and acceptance criteria that govern the pipeline build.

  • CMS query requirements doc — which endpoints or queries, auth, data shape per page type, pagination/multilingual handling
  • Template logic + acceptance criteria — expected output per page type, heading structure, prose density, front-matter fields, bilingual rules
  • Build/deploy requirements — trigger mechanism (webhook, cron, manual), output path (/llms/), CDN/subdomain, llms.txt index spec

Part B — Technical Implementation (~9 days · optionally subcontracted)

Hands-on engineering that builds the automated pipeline from OSP's spec — can be delivered by OSP, the client's technical partner, or a subcontractor.

  • Headless CMS query layer — API calls or database queries to extract content per page type from the Contao stack
  • Markdown templating engine — transforms structured CMS data into prose per the content schema defined in MD-1
  • Bilingual rendering — DE + EN output from the same source data, correctly attributed
  • Build trigger + deploy config — on-publish hook, scheduled cron, or manual dispatch; serve from /llms/ directory, CDN, or subdomain; include llms.txt index
  • Edge case handling — missing fields, draft content, unpublished pages, seasonal content that should/shouldn't appear
Dependency: Requires access to the CMS content model (coordination with the client's technical partner). Part A can begin once Jam's 1A architecture is approved; Part B begins once Part A spec is delivered.
3.03 Output Validation

MD-3: ~2 Days (OSP)

OSP validates the pipeline's output — testing AI-engine citation, comparing schema vs. mirror quality, and iterating on templates.

  • AI-engine citation testing — feed rendered .md files to target engines (ChatGPT, Perplexity, Claude, Gemini, Google AI Overviews) and verify they cite, quote, and synthesize correctly
  • Schema vs. mirror comparison — mirror-fed responses vs. raw HTML crawl. Is the mirror actually improving output on top of schema markup?
  • Bilingual validation — do engines correctly attribute language and avoid cross-contamination between DE and EN?
  • Hallucination audit — does anything in the markdown structure confuse or mislead engines?
  • Template iteration — adjust heading depth, prose density, entity emphasis based on findings
Synergy: Runs alongside Jam's Phase 3 re-run. Same engines, same queries — but now measuring whether the mirror layer adds measurable lift on top of the schema markup.
3.04 Maintenance Handover

MD-4: ~1 Day (OSP)

OSP writes handover documentation so the client's technical partner can maintain and extend the mirror without ongoing consultant involvement.

  • Pipeline architecture doc — what runs, where, how to trigger a rebuild
  • New page type guide — how to add a new page type to the mirror (template + CMS query)
  • QA process spec — spot-check cadence, what to test after content updates, lightweight validation script
